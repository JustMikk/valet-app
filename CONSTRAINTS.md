# Constraints

Last reviewed: 2026-10-22 by @Mikiyas

The quality bar for this repo. Every check blocks: a failing check is fixed in the code, never by
editing this file in the same change. Tightening is welcome; loosening needs the owner's sign-off
in its own commit, and `pnpm guard` flags it. Sources: build handoff §7 (code quality), §5.1
(Capacitor-ready), §5.3 (layers), §8.3 (evidence).

## Floor (always enforced)

- No new suppression comments: `@ts-ignore`, `@ts-nocheck`, `eslint-disable`, `istanbul/v8/c8 ignore`, `nosemgrep`, `gitleaks:allow` (handoff §7: "do not silence lint rules")
- No unimplemented stubs: `throw new Error("Not implemented")`, empty `catch {}`, `TODO`/`FIXME` left in code
- No skipped or deleted tests, and no test file left with fewer assertion lines than before (rewording or strengthening one is fine; the guard counts net per file, so review still checks that a replacement is not weaker)
- No secrets in source or history (reported redacted, never by value)
- No new path in `.constraintsignore` without an Exceptions row
- This file does not get weakened to make a change pass

Checked by `pnpm guard` (`scripts/floor-guard.mjs`, diff-scoped, exit 0 clean / 1 violation / 2 could not run) and `pnpm secrets`.

## External opinions

## Build mode (owner-directed, 2026-10-22)

While every page is being built, only the checks that keep the code sound run per task: the floor, types, lint (device APIs, tokens only, component size), architecture boundaries, secrets and the static export build. The following are **deferred to the testing phase after the full build**, not dropped:

- Unit, component and end-to-end tests for new pages and logic, and the changed-line coverage gate that depends on them (existing tests stay and are run in `check:full`).
- Lighthouse, per-route bundle budgets, the axe and keyboard-focus run on new routes, and the visual baselines.
- PWA/offline, platform providers, the real data layer and realtime (pages run on typed in-memory fixtures in `src/mocks`).

Still expected while building: semantic markup, labels and keyboard-operable controls, icon plus words for status, and `prefers-reduced-motion` for every animation. The testing phase starts when every page in `tasks/build-all.md` exists; its first task is to restore the rows above to per-task gates. Do not read this section as a lower bar for the floor.

## Known environment issues

- **Vitest worker start-up on Windows.** Vitest's fork pool has a hard-coded 60 s start timeout (`START_TIMEOUT` in vitest 5.0.5). On this Windows laptop the first worker occasionally exceeds it (likely antivirus scanning the new Node process); tests themselves take ~3 s. Rerun once. Do not add test retries or raise timeouts to hide it; if it recurs on CI (Linux), treat it as a real failure.
- **Lighthouse LCP outliers on this Windows laptop.** For the same build, individual LCP samples on `/` are bimodal: about 2.0 s most of the time, with roughly a third of runs landing at 3.0–4.6 s (observed 2026-10-22: 2121, 1982, 3472, 4387, 2170, …). The page and its JS did not change between samples. Ruled out: Chromium background-throttling flags (no change) and the web-font swap (`font-display: optional` made it worse). Cause unknown. The gate uses the median of 5 runs, which passes most runs but still fails roughly one in six when three or more samples are outliers: rerun before treating a single LCP failure as a regression, and check the samples with `LIGHTHOUSE_VERBOSE=1 pnpm perf`. A stable result needs either CI hardware (Linux runner) or gating on the best of N runs, which is an owner decision on the statistic, not made here. Do not raise the 2500 ms budget to hide it.
